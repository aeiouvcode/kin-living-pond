## Problem restatement before coding
Pond Next's two fish sometimes look safely separated in screenshots, but our 90-second centerline proxy cannot prove fin/body clearance, pellet ownership, or long-run state coherence. We need deterministic, non-vacuous evidence of the mechanics before making the pond denser or more beautiful. First prototype a control CLI that drives existing Godot QA flags and captures meaningful values without modifying gameplay. Compare a direct native Godot log parser to a browser-driven state probe as two candidate designs: start with the native path for repeatable seed/viewport control, retain browser only for end-to-end canvas interactions. If actual implementation contradicts this plan, scrap the sketch and restate the test design. Shared code must be readme-first; each plan item has a runnable proof with nonzero sample counts, finite values and expected outcomes.

Standing plan-in-code rule: write the specific problem here before code; test unresolved ideas empirically; for architecture changes compare multiple designs; maintain `control-kin.mjs` (doctor/snapshot/screenshot/wait-settle/interact, JSON out, `--dry-run` before destructive actions) and map user-visible features to those commands in FEATURE-MAP.md. Do not rewrite stable code merely to conform.

## Cycle 62 problem restatement (fluid logic)
Rapid drag/touch events can enqueue ripple impulses faster than the GPU consumes eight per frame. The current `pending` array has no bound, so old touches can render much later and memory grows under a sustained flood. Candidate A drops every impulse after a full queue (loses the newest user's touch). Candidate B keeps the latest bounded 32 impulses, discarding oldest stale ones; test B in an isolated Godot water-lab fixture before pond integration. Pass proof: enqueue 100 known impulses with GPU path enabled, assert queue count 32 and oldest/newest IDs 68/99; drain four batches of eight and assert exactly 32 delivered, final queue empty. Also compare solo water and Pond Next 390x844 / true 1280x800 pixels in normal interaction, with no shader errors. Record any responsiveness or visual regression before retention.

## Cycle 63 problem restatement (fish/feeding logic)
A pellet can be stranded outside fish steering reach (a valid tap near the viewport edge projects to a world position beyond the soft wall). `food` has a six-pellet cap and no expiry, so six uneaten pellets could permanently suppress future feed taps. Candidate A clamps all food to reachable water, which detaches the pellet from the user's actual tap. Candidate B gives uneaten pellets a forgiving 40-second lifetime, then removes them and frees a slot; normal eating continues immediately. Test B in a headless pond method fixture at 39.9/40 seconds with mixed ages, verify actual node cleanup and cap reopening, then native solo fish and Pond Next renders at 390x844 / true 1280x800 and the existing two-pellet interaction.

## Cycle 64 problem restatement (fluid QA/control isolation)
The native screenshot command changes `godot/project.godot` in place to set true desktop dimensions. If the shell/process is killed before `finally`, the repo keeps a wrong viewport and an orphan lock. This occurred in c63; water/pond evidence from the next cycle can silently use wrong dimensions. Candidate A adds signal hooks, which cannot cover SIGKILL or host interruption. Candidate B runs with a temporary isolated project root: copy the project config with target viewport and symlink only known project resources into `/tmp`; Godot writes its import cache there, and the canonical repo config never changes. Validate normal phone/desktop renders, abrupt SIGKILL (canonical config/hash unchanged, no orphan lock), screenshots and failure paths, then solo water/Pond Next pixels at both sizes. Keep the same argv and proof contract; reject if Godot cannot resolve resource paths safely.

## Cycle 67 problem restatement (fish spacing failure)
The hard-gap correction handles only `dl > 1e-4`. If two fish begin at the same body/veil centerline (or numerical proximity below that threshold), `dv` has no direction and the guard does nothing. Candidate A picks a random vector, which makes a replay nondeterministic. Candidate B uses stable per-fish indexed opposite lateral vectors to separate from exact coincidence, while preserving normal distance-based correction. Prototype a small pure steering helper and assert equal/opposite finite separation at zero distance, then native two-pellet regression and solo fish/Pond Next phone/desktop pixels. Reject if the helper changes normal separation or causes a visual jump.

## Cycle 68 problem restatement (fluid input boundary)
Water input maps mouse/touch coordinates directly to normalized UV, but a drag can leave the viewport while held. `_drop` queues off-canvas impulses that still consume an eight-per-frame GPU slot, and nonfinite externally supplied coordinates could poison the shader. Candidate A clamps to the rim, causing a visible false ripple at the edge; candidate B rejects invalid/off-canvas drops before either GPU or CPU path. Test B with actual `_drop` calls for in-range boundary, out-of-range and nonfinite UV, ensuring no queue change for rejects and normal queue order for valid touches; then solo water and Pond Next fixed phone/desktop renders. No network or new input route.

## Cycle 70 problem restatement (fluid surface)
The surface drawn over fish is faint and uniform: a 0.06 aqua veil plus low reflection, while the floor's bright caustic net dominates. Candidate A increases uniform veil alpha, previously blurred fish in c52. Candidate B introduces a broad, low-contrast specular band controlled by the moving swell, masked away from fish-heavy center, so the surface plane reads over the floor but does not flatten the fish. Test B first on Pond Next phone, then solo water/desktop only if actual pixels show spatially coherent water rather than pale chips. Preserve baseline on rejection.

## Cycle 71 problem restatement (fish geometry QA)
Solo fish images cannot prove that the procedural body/fin meshes have finite vertices, normals or nondegenerate triangles. A malformed procedural mesh can make a fin vanish at a different camera angle despite a plausible overhead render. Candidate A relies on screenshots only; candidate B runs a headless inspection of the actual generated fish meshes, counting triangles, finite vertices/normals, and degenerate faces for both species, then uses solo and integrated pixels at phone and desktop. If the QA finds intentional degeneracies, classify them rather than writing a vacuous all-green assertion. Keep gameplay source unchanged unless a concrete defect is found.

## Cycle 72 problem restatement (fluid queue drain)
Cycle 62 proved a bounded pending impulse array but copied the drain logic into its test rather than exercising `_gpu_step`. A future edit could silently alter eight-per-frame delivery while the test still passes. Candidate A leaves the copied fixture as is; candidate B extracts only batch consumption into a method used by `_gpu_step` and the fixture, then proves 100 -> 32 newest -> four exact ordered batches -> zero. Reject if renderer behavior or phone/desktop water/pond pixels differ, and keep mobile GPU as unverified.
